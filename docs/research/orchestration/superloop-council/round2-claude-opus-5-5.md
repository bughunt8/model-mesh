# Round 2, the Explainer (Claude Opus 5.5): unplug the inner engine, then check the doors

## 1. The point I now accept

The Researcher's point: `bunx oh-my-openagent run` exits only when the session is idle, todos are done and no continuation hook is active, so it "absorbs omo's internal loops, which conflicts with letting the outer driver own continuation." My round 1 command line used exactly that wrapper. Think of a car with two drivers and one accelerator: the superloop counts laps while omo's hooks keep pressing the pedal, so my caps were counting the wrong laps.

When I traced the wrapper's source, the change went further than the Researcher's version. At the pinned v4.19.4, the exit test returns false while any todo is incomplete, unless a todo-hook marker exists ([completion.ts](https://github.com/code-yeongyu/oh-my-openagent/blob/v4.19.4/packages/omo-opencode/src/cli/run/completion.ts)). The poll loop has no deadline of its own: it returns 0 on completion and 130 only on abort ([poll-for-completion.ts](https://github.com/code-yeongyu/oh-my-openagent/blob/v4.19.4/packages/omo-opencode/src/cli/run/poll-for-completion.ts)). That means the round 2 consensus (the wrapper with hooks disabled) builds a turnstile that opens only when the to-do list is empty, and then fires the cleaner who empties it. A worker that stops with open todos waits there until the watchdog kills it. The fix is in D1.

## 2. Claims I reject

**"todoContinuationEnforcer caps continuations at 8" (Adversarial) and "boulder capped at 8" (Practical).** The 8 exists, but in a different edition. Commit 3a56234 is "feat(omo-senpi)", and the cap of 8 applies to senpi's `start-work-continuation` ([omo commit](https://github.com/code-yeongyu/oh-my-openagent/commit/3a56234e33d5eab69bc55eea40e16cc79135316d)). The OpenCode edition the repo pins stops after 3 stagnant continuations or 5 consecutive failures, and it keeps no lifetime count ([v4.19.4 constants](https://github.com/code-yeongyu/oh-my-openagent/blob/v4.19.4/packages/omo-opencode/src/hooks/todo-continuation-enforcer/constants.ts)). A brake that only trips when the car stands still will never trip for a car driving in circles. The Adversarial's `/ralph-loop` is also gone at v4.19.4: that version's hook guide says `/ralph-loop`, `/ulw-loop` and `/cancel-ralph` "were removed" and that `ralph-loop/` is unwired ([v4.19.4 hooks guide](https://github.com/code-yeongyu/oh-my-openagent/blob/v4.19.4/packages/omo-opencode/src/hooks/AGENTS.md)).

**"A default continuation cap of 100" (Researcher), and the Practical's round 2 claim that both readings were true for their versions.** On every version I checked, 100 is a dial that isn't connected to anything. The Goal hook's index, controller, store and types files are byte-identical at v4.19.4 and dev, and none of them reads configuration or counts iterations ([v4.19.4 hook](https://github.com/code-yeongyu/oh-my-openagent/blob/v4.19.4/packages/omo-opencode/src/hooks/goal/index.ts), [dev hook](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/packages/omo-opencode/src/hooks/goal/index.ts)). The v4.19.4 schema comment calls the key the "Default continuation iteration cap" ([v4.19.4 schema](https://github.com/code-yeongyu/oh-my-openagent/blob/v4.19.4/packages/omo-opencode/src/config/schema/goal.ts)). The v5.1.48 and dev docs correct that: "the Goal hook doesn't enforce an iteration cap" ([dev features](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/reference/features.md)).

**`opencode run --agent sisyphus` (First-Principle, Researcher and Adversarial, round 1).** omo registers Sisyphus in the host as "Sisyphus - ultraworker" ([agent-display-names.ts](https://github.com/code-yeongyu/oh-my-openagent/blob/v4.19.4/packages/omo-opencode/src/shared/agent-display-names.ts)), and omo warns that `opencode run --agent` "does exact-key lookup in the host" ([omo CLI](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/reference/cli.md)). OpenCode's own page doesn't say what happens with an unknown agent ([OpenCode CLI](https://opencode.ai/docs/cli/)). It's like addressing a letter to "Sisyphus" when the mailbox reads "Sisyphus - ultraworker": it may bounce, or it may land with the default agent. No one on the council has tested which.

**Other disputed facts, re-verified**

- **TypeSafe retention:** each side is half right. The DPA keeps data "for as long as necessary taking into account the purpose of the Processing" ([TypeSafe DPA](https://typesafe.ai/legal/data-processing)). That is a criterion, not a period. TypeSafe offers ZDR "for enterprise customers" ([TypeSafe legal](https://docs.typesafe.ai/legal.md)), and retention depends on "any agreed Zero Data Retention (ZDR) arrangement" ([TypeSafe help](https://help.typesafe.ai/articles/5974925716-how-is-submitted-data-used-or-retained)). So "no published policy" is wrong, but so is "a period you can plan around".
- **madewithjev:** written by Jon Kraayenbrink, the site says it "is independent and not affiliated with TypeSafe AI", yet its sponsor footer lists Jev products ([Made with Jev](https://madewithjev.com/jev-multi-agent)). It's independent of the vendor but not neutral about Jev. Treat it as a practitioner guide, not as evidence.
- **ScaleDown:** confirmed. "Only `state.text` / `state.document` are read", each question runs as its own classify call, and `usage` is "the sum of every internal call's tokens" ([ScaleDown overview](https://docs.scaledown.ai/api-reference/decisions-overview)). My inference: if billing follows usage, five questions on one state pay for that state about five times.
- **Jev 1.14:** 64k tokens per request and 32k per question. With the long-context header, both limits become 262k ([Jev models](https://docs.typesafe.ai/models)).
- **Laya:** the English checkpoint has 512 tokens, but 192 go to options, which leaves "~320 tokens for state". The typed-decisions checkpoint has 1,024 tokens and about 768 for state ([Laya card](https://huggingface.co/convaiinnovations/laya)). The Adversarial's sanitized state runs to 380 tokens, which is a 380-word letter in a 320-word envelope.

## 3. Positions

**D1.** The outer driver owns continuation. Materialize `"disabled_hooks": ["goal", "todo-continuation-enforcer", "start-work", "atlas"]`, all of which are valid hook names at v4.19.4 ([v4.19.4 configuration](https://github.com/code-yeongyu/oh-my-openagent/blob/v4.19.4/docs/reference/configuration.md)). Run a driver-owned `opencode serve --port P` with a private HOME and config ([OpenCode CLI](https://opencode.ai/docs/cli/)). Each iteration then runs: `timeout -k 30 600 bunx oh-my-openagent run --attach http://127.0.0.1:P --agent sisyphus --json --directory <worktree> "<prompt>"`. The driver polls the same server for session status and todos. If the session sits idle with open todos for 60 seconds, the driver sends SIGINT (exit 130) and logs `idle_open_todos` instead of waiting out a hang. The wrapper keeps its one useful job, which is waiting for child sessions, and the dry run has to show that children still finish with `atlas` disabled. Exit 0 means quiet, not done.

**D2.** Stay on v4.19.4 OpenCode for this PR and leave 5.x to a separate adapter PR. I could find `default_max_iterations` enforced nowhere, so the driver's cap is the only cap.

**D3.** Yes. Once a decider can dispatch or gate, it counts as an orchestrator for family purposes, across every rung and the run's whole lineage. A Qwen-derived decider is alibaba. A Gemma-derived one is google, which the validator lists as Hong Kong blocked ([validator](https://github.com/bughunt8/model-mesh/blob/daf9ac42a9e86700a2f6c1c8b10353cd998a2a09/scripts/validate-orchestration.py)). Unknown lineage fails. A log-only shadow seat is exempt from the family rule, the way a passenger with a notebook needs no driving licence. It still needs a passport, though: under ultimate, shadow calls send state abroad, and its output must never reach an acting agent.

**D4.** Use an owner-approved escalation ladder; the model may only request a step. The First-Principle's A01 point holds: ultimate's A01 primary uses `deepseek-v4-pro` as the atlas author, while hybrid's uses it as the momus reviewer ([MATRIX.md](https://github.com/bughunt8/model-mesh/blob/daf9ac42a9e86700a2f6c1c8b10353cd998a2a09/docs/research/orchestration/MATRIX.md)). Filter every rung against a cumulative provenance ledger. omo also fails open: "Activating a profile that does not exist produces a diagnostic and falls back to the base configuration" ([v4.19.4 configuration](https://github.com/code-yeongyu/oh-my-openagent/blob/v4.19.4/docs/reference/configuration.md)). The driver must check the effective config after every switch.

**D5.** Done authority stays an advisory smoke detector. If the sensors are green and P(done) is low, that triggers an early review. It can never block or certify.

**D6.** Run Learn-then-Test before activation, and keep point values as shadow labels only. One audit found that point-chosen gates broke their promise in 147 of 190 evaluations while Learn then Test kept it in all 190, and that an en-US 95% promise held in only 8 of 51 locales ([Brom audit](https://arxiv.org/html/2610.36311v1)). The vendors use the same word for different thermometers. Jev's Choice confidence is \((p_{\max}-1/n)/(1-1/n)\) ([Jev confidence](https://docs.typesafe.ai/confidence.md)). ScaleDown's is the chosen option's probability ([ScaleDown decisions](https://docs.scaledown.ai/api-reference/decisions)). Noul returns no confidence field at all. Over A01 to A12, a Jev reading of 0.80 means \(p_{\max}\approx0.82\); for a yes/no Choice it means 0.90. Calibrate separately for each backend, model version, question revision and locale.

**D7.** 10 outer iterations, 30 minutes of wall clock, a no-progress streak of 2 (unchanged evidence hash) and 3 fix-verify cycles. I'm dropping my 12 and my 3 to the council's values, since no member has data for better numbers.

**D8.** Add the checks now, but put them in a superloop config validator rather than adding O19+ to the matrix. The Practical is right that a matrix rule for a seat that doesn't exist is noise, while a run config does have a decider field. The validator should reject: no finite cap, a decider as done authority, alias IDs such as `jev-latest`, an unknown-family decider outside shadow, and a decider that isn't HK-reachable under ultimate.

**D9.** Neither CDM product goes in. Ship the offset check `raw[start:end] == span` as a state-builder contract, tested with fixtures, so code parsers work today and Extract or GLiNER can plug in later. Summarize and Compress appear nowhere in this PR.

**D10.** "The superloop is a standing service: it keeps taking goals, but each goal ends on verified evidence, a cap or a hand-back, and only I renew a cap."

**D11.** Disproved in all six patterns. It holds for the orchestrator seat itself, which in model-mesh writes plans and prompts. A System One model is the signalman, not the train driver.

## 4. Corrections to my round 1

- I wrote that v4.19.4's key "is the continuation iteration cap" and that the treadmill's timer "may vanish on the next upgrade". The docs said so, but the code never had that timer, so there was nothing to lose.
- My worker command absorbed omo's loops. D1 replaces it.
- My stall threshold drops from 3 to 2. My point thresholds become uncalibrated shadow labels, and my routing rule "top P >= 0.80" never said which confidence it meant.
- Retention: "DPA with retention terms" should read "a retention criterion with no period, plus ZDR by enterprise agreement".
