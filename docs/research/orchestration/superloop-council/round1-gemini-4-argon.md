# Round 1 council report: the adversarial (Gemini 4 Argon)

Date: 2026-10-28. Persona: The Adversarial. Target repository: `github.com/bughunt8/model-mesh` on branch `orchestration/egm-lenses-and-gates`.

The prompt commits two opposite errors. First, it sets up a strawman that System One models have "no place" in the six patterns from [Anthropic's "Building effective agents"](https://www.anthropic.com/research/building-effective-agents), ignoring Anthropic's classification and gate steps. Second, it leaps to an indefensible proposal: putting Jev or System One at the core as the orchestrator driving `oh-my-openagent` (omo) profiles in an "endless loop". A model that cannot emit prose, write plans, construct commands, or explain failures cannot orchestrate workers, and wiring a probabilistic classifier into an "endless loop" stop condition breaks `model-mesh` verification.

## Hypothesis test across the six Anthropic patterns

A System One model takes a `state` and typed `questions`, returning calibrated probabilities across `choice` (up to 255 options with probabilities and confidence), `score` (expected value and probabilities across an ordered rubric), and `noul` (boolean probability in `[0, 1]`), with zero generated text ([TypeSafe System One docs](https://docs.typesafe.ai/concepts/system-one); [TypeSafe primitives reference](https://docs.typesafe.ai/primitives)).

Testing the hypothesis ("there is no place for JEV or System One in the 6 Agentic flows") against [Anthropic's definitions](https://www.anthropic.com/research/building-effective-agents) yields a split verdict: **partly disproved** overall (**disproved** in three patterns with pre-enumerated control forks, **partly disproved** in two where System One fits only as a stop-gate or brake, and **holds** at the generative core of task breakdown and feedback).

### 1. Prompt chaining

- **Anthropic's wording.** "Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one. You can add programmatic checks (see "gate" in the diagram below) on any intermediate steps to ensure that the process is still on track." ([Anthropic, "Building effective agents"](https://www.anthropic.com/research/building-effective-agents)).
- **System One fit and exact decision.** Fits semantic gates: `gate_pass` (`noul` "Does the artifact satisfy stage requirements without ungrounded claims?", `>= 0.85` advances); `stage_quality` (`score` over `["0: missing", "1: partial", "2: complete"]`, `score >= 1.7`, `confidence >= 0.75`); and `failure_action` (`choice` over `["retry_step", "switch_fallback_chain", "abort_to_human"]` when `gate_pass < 0.85`).
- **Cannot do.** Generate step outputs, transform data, or explain failures.
- **Verdict.** **Hypothesis disproved.**

### 2. Routing

- **Anthropic's wording.** "Routing classifies an input and directs it to a specialized followup task... Routing works well for complex tasks where there are distinct categories that are better handled separately, and where classification can be handled accurately, either by an LLM or a more traditional classification model/algorithm." ([Anthropic, "Building effective agents"](https://www.anthropic.com/research/building-effective-agents)).
- **System One fit and exact decision.** Direct match, including model-tier routing ([Anthropic, "Building effective agents"](https://www.anthropic.com/research/building-effective-agents)): `triviality_gate` (`noul` "Is the task 1 file, <10 lines, with no new behavior or lookup?", `>= 0.90` bypasses the loop per [skills/mm-method/SKILL.md](../../../../skills/mm-method/SKILL.md)); `situation_id` (`choice` over `["A01".."A12"]` in [docs/ORCHESTRATION.md](../../../ORCHESTRATION.md), accept if `confidence >= 0.70`, else `A09` or human grill); and `profile_tier` (`choice` over `["b4b", "hybrid", "ultimate"]` given complexity `score` `0..2`).
- **Cannot do.** Execute specialist prompts or rewrite input.
- **Verdict.** **Hypothesis disproved.** Strongest fit across all six patterns.

### 3. Parallelization (sectioning and voting)

- **Anthropic's wording.** "LLMs can sometimes work simultaneously on a task and have their outputs aggregated programmatically. This workflow, parallelization, manifests in two key variations: Sectioning: Breaking a task into independent subtasks run in parallel. Voting: Running the same task multiple times to get diverse outputs." ([Anthropic, "Building effective agents"](https://www.anthropic.com/research/building-effective-agents)).
- **System One fit and exact decision.** Fits guardrails, worker pruning (NeuroSploit DP3 in [Santos, arXiv:2609.28940v1](https://arxiv.org/html/2609.28940v1)), and voting over fixed candidates: `lens_relevant_{i}` (`noul` per lens `i`, `>= 0.40` kept, keeping primary lens); `safety_guardrail` (`noul` on external state/auth boundary, `>= 0.20` halts); and `cluster_vote` (`choice` over `["confirmed", "needs-review", "rejected"]` plus `noul` for `demonstrated_impact`, `p(confirmed) >= 0.80` and `p(impact) >= 0.70`, per NeuroSploit DP1 in [Santos, arXiv:2609.28940v1](https://arxiv.org/html/2609.28940v1)).
- **Cannot do.** Partition features into new subtask prompts or merge free-text findings across divergent line ranges ([scripts/aggregate-findings.py](../../../../scripts/aggregate-findings.py)).
- **Verdict.** **Hypothesis disproved** for voting, guardrails, and worker pruning; **holds** for subtask authoring.

### 4. Orchestrator-workers

- **Anthropic's wording.** "In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results... Whereas it's topographically similar, the key difference from parallelization is its flexibility, subtasks aren't pre-defined, but determined by the orchestrator based on the specific input." ([Anthropic, "Building effective agents"](https://www.anthropic.com/research/building-effective-agents)).
- **System One fit and exact decision.** **Not as the orchestrator.** Subtasks are not pre-defined ([Anthropic, "Building effective agents"](https://www.anthropic.com/research/building-effective-agents)), whereas System One requires pre-enumerated `criteria` ([TypeSafe launch post](https://typesafe.ai/blog/introducing-system-one-models-and-jev)). It can only act as a **post-planning dispatcher** after `prometheus` or `sisyphus` writes subtasks: `assign_category` (`choice` over the 8 omo categories, `confidence >= 0.65`, else `unspecified-high`) and `event_triage` (`choice` over `["route_to_subagent", "queue_for_batch", "wake_planner_llm"]` per [Made with Jev multi-agent guide](https://madewithjev.com/jev-multi-agent)).
- **Cannot do.** Dynamic task decomposition, prompt generation, and result synthesis.
- **Verdict.** **Hypothesis holds for the core orchestrator seat; partly disproved only for post-planning category dispatch.**

### 5. Evaluator-optimizer

- **Anthropic's wording.** "In the evaluator-optimizer workflow, one LLM call generates a response while another provides evaluation and feedback in a loop... The two signs of good fit are, first, that LLM responses can be demonstrably improved when a human articulates their feedback; and second, that the LLM can provide such feedback." ([Anthropic, "Building effective agents"](https://www.anthropic.com/research/building-effective-agents)).
- **System One fit and exact decision.** Only as the stop/continue gate. Anthropic's evaluator must *articulate feedback*, and [examples/orchestration/finding.schema.json](../../../../examples/orchestration/finding.schema.json) requires text `claim` and `evidence` fields. System One only scores exit readiness: `iteration_verdict` (`choice` over `["accept", "refine_again", "escalate_human"]`, `p(accept) >= 0.85` when deterministic checks pass) and `rubric_score` (`score` over `["0: fails spec", "1: minor defects", "2: meets spec"]`, `score >= 1.8`).
- **Cannot do.** Articulate critique text, emit `finding.schema.json` objects, or revise artifacts.
- **Verdict.** **Hypothesis partly disproved.**

### 6. Autonomous agents

- **Anthropic's wording.** "Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks... They are typically just LLMs using tools based on environmental feedback in a loop." ([Anthropic, "Building effective agents"](https://www.anthropic.com/research/building-effective-agents)).
- **System One fit and exact decision.** Only as an action guardrail, drift monitor, or finite-menu selector (DOM index selection in `Jev-Ultrafast` in [Santos, arXiv:2609.28940v1](https://arxiv.org/html/2609.28940v1) or key choice in [`stephenlb/system-one-model`](https://github.com/stephenlb/system-one-model)). It cannot construct bash commands or edits; it only scores `action_autonomy_tier` (`score` `0: read` to `4: irreversible` per [Made with Jev multi-agent guide](https://madewithjev.com/jev-multi-agent), halting at `>= 2.5` for `AUTH:`) and `loop_spinning` (`noul >= 0.75` aborts).
- **Cannot do.** Write code, construct shell commands, or recover from novel stack traces.
- **Verdict.** **Hypothesis partly disproved.**

## Stress-testing the proposal: "System One at the core, omo profiles in an endless loop"

Taken literally, the proposal fails on three counts:

1. **Control plane versus planner.** In `model-mesh`, the `orchestrator` seat (`sisyphus` in P1, P2, and P5) writes plans, worker prompts, and merges ([docs/ORCHESTRATION.md](../../../ORCHESTRATION.md)). Because System One cannot emit text ([TypeSafe System One docs](https://docs.typesafe.ai/concepts/system-one)), replacing `sisyphus` with Jev leaves workers without instructions. As [Made with Jev](https://madewithjev.com/jev-multi-agent) states: "Does Jev replace the orchestrator? No. The surrounding system owns the workflow. Jev owns one fuzzy decision inside it." The sound design is **a deterministic Python driver (`omo-superloop.py`) that owns the outer loop and queries System One at bounded control forks, while each omo profile retains `sisyphus` inside the worker session.**
2. **"Endless loop" violates repo invariants.** `mm-loop` caps fix-verify cycles at 3 ([skills/mm-loop/SKILL.md](../../../../skills/mm-loop/SKILL.md)), `mm-method` caps review-fix rounds at 2 ([skills/mm-method/SKILL.md](../../../../skills/mm-method/SKILL.md)), and OMO's `todoContinuationEnforcer` caps continuations at 8 ([DeepWiki OMO 10.4](https://deepwiki.com/code-yeongyu/oh-my-openagent/10.4-ralph-loop-and-todo-enforcement)).
3. **Probabilistic stopping is not verification.** Asking `noul("Is the goal met?")` on an agent's summary violates [skills/mm-verify/SKILL.md](../../../../skills/mm-verify/SKILL.md) ("a report is a set of claims, not evidence").

### Stopping, budgets, safety, and human gates

Loop exit requires **deterministic verification first** (exit `0` on `--verify-cmd`, schema-valid findings, and `0` blockers in [scripts/aggregate-findings.py](../../../../scripts/aggregate-findings.py)). Enforce hard caps: `max_iterations = 5`, `max_fix_cycles = 3` per cluster, and a two-turn **identical diff-hash or test-signature circuit breaker** halting regardless of probabilities. Start on `b4b` or `hybrid` (`$4.65/1M` output cap in [scripts/validate-orchestration.py](../../../../scripts/validate-orchestration.py)), with at most one escalation to `ultimate`. Under [skills/mm-method/SKILL.md](../../../../skills/mm-method/SKILL.md), outward or irreversible actions require a verbatim `AUTH: user said "<quote>"` record. System One is only a **one-way brake**: if `noul(needs_human_auth) >= 0.20` or `score(autonomy_risk) >= 2.5`, the driver halts for human approval, and `0.00` never bypasses a missing `AUTH:` quote ([Made with Jev](https://madewithjev.com/jev-multi-agent)).

### The independence trap (rules O4, O5, O15, O16, O17)

In [scripts/validate-orchestration.py](../../../../scripts/validate-orchestration.py), Rules O5, O16, and O17 require family disjointness across orchestrator, authors, reviewers, and aggregator, and Rule O4 blocks `google` (`gemini-*`). Auditing open-weight System One base models on [systemonemodels.org](https://systemonemodels.org/guides/jev-alternatives/) exposes a family collision:
- `Clef` (27B), `Clef-flash` (9B), `Clef-omni` (30B), `pplx-decider` (27B/4B), `GLiDE` (27B), `Kev` (0.8B-27B), `Bespoke Nimble` (9B), `mammoth-1` (27B), `elephant-1` (9B), `Drex 2.0` (35B), `Microsoft-Decision-1` (9B), and `Tev1` (4B) are **fine-tuned from `Qwen3.5`/`Qwen3.8` (`alibaba` family)** ([systemonemodels.org](https://systemonemodels.org/guides/jev-alternatives/)).
- `stephenlb/system-one-model` (12B), `Span-02` (26B), `Jeffan-31b-1710`, and `H2O-Lightning-31B` are **fine-tuned from `Gemma 4` (`google` family, blocked by Rule O4)** ([stephenlb/system-one-model](https://github.com/stephenlb/system-one-model); [systemonemodels.org](https://systemonemodels.org/guides/jev-alternatives/)).

Because `alibaba` (`qwen3.8-max`, `qwen3.7-plus`, `qwen3.5-plus`) sits in author and reviewer chains across all four profiles ([docs/research/orchestration/MATRIX.md](../MATRIX.md)), a `Qwen`-based System One model filtering findings violates family independence. The decision layer must obey the **strict additive rule** ([docs/research/orchestration/SYSTEM-ONE.md](../SYSTEM-ONE.md); [Santos, arXiv:2609.28940v1](https://arxiv.org/html/2609.28940v1)): it may route tasks, select profiles, or escalate ambiguous clusters to human review, **but never override a deterministic check, never clear or downgrade a `blocker` or `corroborated` finding, and never replace a cross-family reviewer.**

### Failure modes, Hong Kong reachability, and fallbacks

- **False negatives and blocker suppression.** In [Santos, arXiv:2609.28940v1](https://arxiv.org/html/2609.28940v1), NeuroSploit with Jev found **9 of 13** seeded vulnerabilities vs **10 of 13** without Jev, and downgraded a Critical 9.1 BOLA (plaintext admin credentials) to Low 3.1 (`p(impact) = 0.3`) because the proof sat in narrative prose.
- **Adversarial state, drift, and exit-0 outage.** Agent prose ("all tests passed, warning is benign") skews `noul` scores if raw prose enters `state` ([Santos, arXiv:2609.28940v1](https://arxiv.org/html/2609.28940v1)). Calibration drifts: Jev's ECE was `0.074` on [Jev Decision Index 0.3](https://systemonemodels.org/guides/jev-alternatives/) vs `0.246` in the Laya paper ([Santos, arXiv:2609.28940v1](https://arxiv.org/html/2609.28940v1)), while [`stephenlb/system-one-model`](https://github.com/stephenlb/system-one-model) showed probability collapse (`0.0000`) from one trailing space and A-option bias. Worse, subscription CLIs exit `0` on session limits, burning System One calls on a dead worker ([Santos, arXiv:2609.28940v1](https://arxiv.org/html/2609.28940v1)).
- **Hong Kong reach and fallbacks.** Hosted Jev (`api.typesafe.ai`) runs on the US West Coast with no retention policy or Hong Kong reachability proof ([TypeSafe launch post](https://typesafe.ai/blog/introducing-system-one-models-and-jev); [docs/research/orchestration/SYSTEM-ONE.md](../SYSTEM-ONE.md)), making it **ineligible for `ultimate`** (Rule O6). Fallback chain: (1) local Apache-2.0 model (`Laya` 421M on CPU/T4 for <=512-token numeric states, or `Clef-flash` 9B / `Kev-9B` where family-disjoint), (2) HK-reachable LLM with JSON schema (`glm-5.3-flash` or `deepseek-v4-flash`, `calibrated: false`), and (3) deterministic Python rules over exit codes and `aggregate-findings.py` counts.

## CDMs and constrained decoding

The owner's addendum ([ADDENDUM-CDM.md](addendum-cdm.md)) exposes a marketing conflation: "Constrained Decoding Models (CDMs)" is ScaleDown's product label launched on 2026-10-13 ([LangChain blog](https://www.langchain.com/blog/building-long-running-agents-with-scaledown-and-deep-agents); [ScaleDown docs](https://docs.scaledown.ai/introduction)), whereas constrained decoding (CD) in research ([Chavan, arXiv:2609.23742](https://arxiv.org/html/2609.23742v1)) is decoding-time token masking (`Outlines`, `XGrammar`) on generative LLMs ([ibl.ai analysis](https://ibl.ai/blog/constrained-decoding-models-not-a-new-architecture)):

1. **Grammar-constrained decoding (CD) on small generative LLMs ([Chavan, arXiv:2609.23742](https://arxiv.org/html/2609.23742v1)).** Across five 0.6B-4B models (`Qwen3-0.6B`, `Llama-3.2-1B`, `Llama-3.2-3B`, `Phi-4-mini`, `Qwen3-4B`) and 14 tasks (210 evaluations, greedy decoding), CD lifts schema validity from `78.6%-92.9%` to `100%` (`XGrammar` compiles schemas in `4-8 ms` at `1.6%-3.7%` throughput cost; `Outlines` takes `2.0-4.9 s` at `9%-13%` cost) and fixes type-coercion bugs (`"4.98"` -> `4.98`). Yet **instruction-semantic failures remain unfixed** (`Qwen3-0.6B` scores `0.200` native and `0.200` under CD on two-step function calling), and `Llama-3.2-1B` under `XGrammar` shows **"hollow rescue"**, scoring `1.000` structurally while emitting `"1. 2. 3. 4. 5."` as the email body ([Chavan, arXiv:2609.23742](https://arxiv.org/html/2609.23742v1)). Per Chavan ("Schema conformance is necessary but not sufficient for semantic correctness; CD's reach ends exactly where schema conformance ends"), `aggregate-findings.py` and the driver must verify **semantic grounding** (quoted `evidence` spans must exist in the file at `line_start..line_end`), not just JSON schema validity.
2. **ScaleDown's pointing and classification models (`Classify-1` and `Extract`) vs open-weight `GLiNER2.5`.**
   - **Fit and additions.** `Classify-1` fits the same Routing, Prompt-Chaining gate, and Autonomous-Agent drift-breaker seats as Jev, adding a 1M-token window, image/PDF input, and a one-sentence `reasoning` string on `/classify` (used in the [LangChain blog's](https://www.langchain.com/blog/building-long-running-agents-with-scaledown-and-deep-agents) `@after_model` circuit breaker halting when `top_label != "progressing"` and `score > 0.8`). `Extract` pulls entities with confidence and **character offsets (`start`, `end`)** ([ScaleDown Extract overview](https://docs.scaledown.ai/api-reference/extract-overview)), pulling error codes, failing tests, and paths from 1M-token logs with verifiable offsets before calling a 32K-limit decision model.
   - **Two traps in `/v1/scaledown`.** [ScaleDown's Decisions overview](https://docs.scaledown.ai/api-reference/decisions-overview) shows two breaking differences from Jev: (a) `/v1/scaledown` **ignores multi-field JSON `state` objects**, reading *only* `state.text` and `state.document`; and (b) internally it runs each `choice`, `noul`, and `score` question as a separate `/classify` call and **bills `usage` as the sum of every internal call's tokens**, multiplying input charges by the question count.
   - **Vendor claims vs open-weight reality.** ScaleDown's speed (`200x faster`), cost (`467x cheaper`, `$0.05/M` direct or `$0.04/M` on [OpenRouter](https://openrouter.ai/scaledown)), and accuracy (`77.2%` vs Jev's `72%` on DecisionBench) are vendor claims. On ScaleDown's benchmark page, paid `Extract` leads `GLiNER2.5-multi-v1` (0.3B, Apache-2.0, `480 ms` local CPU, `$0` cost) by **0.2 percentage points**, while Fastino's `GLiNER2.5-Decide` (340M, Apache-2.0, `167.3 ms` CPU) performs non-generative constrained decision scoring locally ([ibl.ai analysis](https://ibl.ai/blog/constrained-decoding-models-not-a-new-architecture)).
3. **ScaleDown's writing models (`Summarize` and `Compress`) risk injection in the decision path.** Unlike `Classify-1` and `Extract`, `Summarize` is an **abstractive generative model** ("a shorter, fluent rewrite in the model's own words", per [OpenRouter](https://openrouter.ai/scaledown) and [ibl.ai](https://ibl.ai/blog/constrained-decoding-models-not-a-new-architecture)), and `Compress` rewrites tool outputs around a `compression_query` ([LangChain blog](https://www.langchain.com/blog/building-long-running-agents-with-scaledown-and-deep-agents)). Putting `Summarize` or `Compress` between worker output and the decision gate inserts an unverified generative rewriter inside the verification path that can drop failing assertions or launder prompt injections. `Summarize` and `Compress` may be used only in untrusted worker context middleware, **never** to build `state` for `s1-decide.py` or reviewers; only host counters and offset-verified spans (`raw[start:end] == span`) from `Extract` or `GLiNER2.5` may enter control-plane state. With no open weights, retention policy, or Hong Kong reachability proof ([ibl.ai analysis](https://ibl.ai/blog/constrained-decoding-models-not-a-new-architecture)), hosted ScaleDown is **barred from `ultimate`** (Rules D46, O6) and limited to an opt-in cross-vendor second vote alongside Jev on `global`, `hybrid`, or `b4b`.

### Script interfaces: `scripts/s1-decide.py` and `scripts/omo-superloop.py`

- **`scripts/s1-decide.py` CLI and backends.**
  `python scripts/s1-decide.py --gate <route|pre_exec|drift|post_exec> --state-file <state.json> --profile <ultimate|hybrid|b4b|global> [--mode <shadow|active|rules>] [--backend <rules|typesafe|scaledown|local-s1|xgrammar-llm|dual-vote>] [--self-test]`.
  For `scaledown` or `dual-vote`, `s1-decide.py` serializes `state` JSON into `state.text` so `/v1/scaledown` preserves all keys ([ScaleDown Decisions overview](https://docs.scaledown.ai/api-reference/decisions-overview)).
- **Sanitized `state.json` (<= 380 tokens).**
  Built from host counters and offset-verified spans (`raw[start:end] == span`), stripping raw prose:
  `{"gate": "post_exec", "profile": "ultimate", "situation": "A01", "iteration": 2, "max_iterations": 5, "same_diff_hash_streak": 0, "diff_files": 2, "diff_lines": 18, "touches_outward_surface": false, "has_auth_quote": false, "checks": {"test_exit": 0, "build_exit": 0, "sentinel_error": null}, "review": {"blockers": 0, "corroborated_majors": 1, "single_majors": 0, "nits": 2, "needs_model_merge": 0, "hollow_evidence_rejected": 0}}`.
- **Exact typed questions and thresholds (`tau`).**
  1. `route` gate: `trivial` (`noul >= 0.90` and `touches_outward_surface == false`); `situation` (`choice` over `A01..A12`, `confidence >= 0.70`, else `A09`); `ambiguity` (`score` `0..2`, halt if `>= 1.5`).
  2. `pre_exec` gate: `autonomy_risk` (`score` `0..4`, halt if `>= 2.5` without `has_auth_quote`); `needs_human_auth` (`noul >= 0.20` halts without `has_auth_quote`).
  3. `drift` gate ([LangChain/ScaleDown circuit breaker](https://www.langchain.com/blog/building-long-running-agents-with-scaledown-and-deep-agents)): `trajectory` (`choice` over `["progressing", "looping", "drifting"]`; trip if `choice != "progressing"` and `probability >= 0.80`).
  4. `post_exec` gate: `next_step` (`choice` over `["accept_done", "retry_same_profile", "escalate_profile", "rerun_review_merge", "halt_human"]`, require `p(accept_done) >= 0.85` and `confidence >= 0.75`).
- **Hard stop and override rules.**
  - **Deterministic veto.** If `test_exit != 0`, `build_exit != 0`, `blockers > 0`, or `corroborated_majors > 0`, override any `accept_done` vote to `retry_same_profile` (or `halt_human` at cap) and log `"override_reason": "deterministic_gate_veto"`.
  - **Stall, sentinel, and budget stop.** Halt if `iteration >= max_iterations` (5), per-cluster fix cycles `>= 3`, `same_diff_hash_streak >= 2`, `sentinel_error != null`, or `trajectory` trips at `>= 0.80`.
- **Non-interactive OMO driver (`scripts/omo-superloop.py`) and offline tests.**
  1. Materializes `profiles/<profile>.json` via `scripts/materialize.py` into `<run_dir>/opencode-config/omo.jsonc`.
  2. Runs worker headlessly in an isolated worktree: `OPENCODE_CONFIG_DIR="<run_dir>/opencode-config" OMO_PROFILE="<profile>" OMO_SEND_ANONYMOUS_TELEMETRY=0 opencode run --dir "<worktree>" --format json --agent sisyphus "<prompt>"` (or `goose run --recipe` / `pi -p --mode json` on `alternate` rows per Rule O9).
  3. Runs `--verify-cmd`, hashes `git diff`, spawns cross-family reviewers (`goose` or `pi`) with **only** frozen diff and lens questions (Rule O15), runs `scripts/aggregate-findings.py` (with hollow-evidence rejection), calls `scripts/s1-decide.py`, and appends a SHA-256 hash-chained entry to `superloop-audit.jsonl`.
  4. Offline `--self-test` (`unittest`, `tempfile`, mocked transports/CLIs) verifies schema checks, `state.text` serialization, deterministic veto of false `accept_done` votes, prose stripping, hollow-evidence rejection, diff-hash stall halt, and `O19`/`O20` enforcement.
- **Out of scope.** System One/CDMs in `matrix.example.json` generative seats; defaulting `--s1-mode` to `active` before shadow evaluation passes; clearing blockers via System One/CDMs; using `Summarize`/`Compress` in verification state; or unbounded loops.
